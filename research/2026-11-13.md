**Angle:** Mengedukasi developer bahwa pemrosesan berkas seperti konversi format bisa dipindahkan sepenuhnya ke browser pengguna menggunakan Browser-Native APIs tanpa server.

**Slide-by-slide:**
1. **Arsitektur Lama yang Membebankan Server** — Saat membangun fitur olah berkas seperti konversi gambar WebP, insting pertama developer biasanya membuat microservice Node.js. Tambahkan bucket S3 untuk penyimpanan sementara dan cron job untuk membersihkan file kedaluwarsa. Padahal arsitektur ini menambah biaya infrastruktur dan beban pemrosesan server.
2. **Memanfaatkan Browser-Native APIs** — Dengan memanfaatkan FileReader API dan Blob di browser, seluruh komputasi pemrosesan file bisa digeser langsung ke client-side. Hasilnya adalah zero infrastructure cost dan privasi data pengguna yang lebih terjamin karena file tidak pernah diunggah ke server luar.
3. **Alur Kerja Memory Pipeline di Browser** — Saat pengguna memilih file WebP lokal, browser akan membuat handle untuk aset tersebut di memori lokal. Tugas kita adalah memproses handle ini secara langsung tanpa memicu HTTP POST request sama sekali ke server backend.
4. **Uji Coba Langsung di WebPNexa** — Arsitektur tanpa backend ini sudah dibuktikan pada utilitas seperti WebPNexa. Aplikasi ini mampu menangani batch processing dan download langsung secara instan hanya dengan memanfaatkan workflow native di frontend.
5. **Ubah Pola Pikir Sebelum Bikin Backend** — Sebelum mulai mengonfigurasi server baru untuk fitur transformasi data deterministik, tanyakan pada timmu: Apakah fitur ini benar-benar membutuhkan backend? Mulailah optimalkan resource di browser pengguna.

### 3. User baru selesai simpan form tapi malah lihat data lama gara-gara database replica belum synchronised? _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Menjelaskan fitur baru Laravel 13.40 yang memungkinkan aplikasi memeriksa posisi commit ID database replica secara langsung untuk mencegah masalah stale database reads.

**Slide-by-slide:**
1. **Masalah Replication Lag di Database** — Aplikasi dengan konfigurasi database read/write menulis ke primary server dan membaca dari replica. Jika replica terlambat menerima sinkronisasi data, pengguna yang baru saja menyimpan form bisa melihat data lama karena query dibaca dari replica yang tertinggal.
2. **Kelemahan Estimasi Time Window** — Laravel 13.38 sempat mengenalkan PreventStaleDatabaseReads middleware dengan jeda 2 detik. Masalahnya, jika lag replikasi lebih lama dari 2 detik, data lama tetap terbaca. Sebaliknya jika lag lebih cepat, request malah tetap dikirim ke primary server.
3. **Solusi Method Baru di Laravel 13.40** — Dikontribusikan oleh Tobias Petry, Laravel 13.40 menambahkan tiga metode koneksi baru: getLastCommitId(), hasCommitId(), dan mergeCommitIds(). Fitur ini memungkinkan aplikasi memeriksa posisi commit ID secara langsung ke server replica.
4. **Cara Kerja Middleware Berbasis Commit ID** — Saat request PUT atau POST selesai menulis data, middleware menyimpan commit ID primary di session. Pada request GET berikutnya, middleware mengecek apakah replica sudah mencapai commit ID tersebut sebelum memutuskan membaca dari replica atau fallback ke primary.
5. **Penerapan pada Queue Worker** — Untuk job yang berjalan tepat setelah operasi write, passing commit ID ke job tersebut dan gunakan method wait pada hasCommitId(). Gunakan usingWritePdo() agar koneksi database kembali normal setelah callback selesai dieksekusi.

**Angle:** Mengajak UI desainer keluar dari kebiasaan grid 12 kolom standar dan mengeksplorasi modular grid untuk membuat antarmuka yang lebih berkarakter.

**Slide-by-slide:**
1. **Jebakan Grid 12 Kolom Standar** — Framework populer seperti Bootstrap dan Foundation memopulerkan grid 12 kolom hingga menjadi standar default antarmuka web. Namun, mengandalkan 12 kolom secara berlebihan sering kali membuat berbagai situs web terlihat persis dan kehilangan keunikan mereknya.
2. **Pahami Karakter Merek Sebelum Menentu Grid** — Sebelum membagi halaman menjadi kolom, pahami kepribadian perusahaan yang sedang didesain. Layout bukan sekadar menata konten, melainkan alat untuk menyampaikan posisi merek, hierarki visual, dan pengalaman emosional pengguna.
3. **Bergerak Dua Dimensi dengan Modular Grid** — Kolom hanya membagi ruang secara vertikal. Dengan menambahkan baris, kita membentuk grid modular yang terdiri dari unit-unit persegi atau persegi panjang. Interseksi ini membuka variasi komposisi ruang yang jauh lebih dinamis.
4. **Studi Kasus Konseptual: Toko Wheelman** — Pada desain toko online Wheelman, penggunaan 16 modul (4 kolom x 4 baris) memungkinkan judul besar dan gambar produk membentang di beberapa modul sekaligus. Sementara fitur belanja dapat diletakkan dalam modul tersendiri untuk menciptakan kontras visual.
5. **Eksplorasi Kontras dan Hierarki** — Jangan ragu memanfaatkan modul untuk mengontrol whitespace dan skala antarmuka. Dengan memvariasikan proporsi antar elemen, tampilan web tetap mudah dinavigasi namun menyajikan kejutan visual yang berkesan bagi pengunjung.
