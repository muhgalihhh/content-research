### 2. Tahu nggak kenapa performa tulis database kamu drop drastis setelah tabel tembus jutaan baris? _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Mengupas masalah performa write IOPS yang hancur akibat penggunaan UUIDv4 pada B-Tree database dan solusi migrasi ke UUIDv7.

**Slide-by-slide:**
1. **Masalah UUIDv4** — Penggunaan UUIDv4 sebagai primary key sering dipilih demi keunikan global, tapi justru memicu I/O nightmare pada storage engine.
2. **Dampak pada B-Tree** — Karena 122 dari 128 bit UUIDv4 bersifat acak, setiap insert baru mendarat di posisi acak dalam B-Tree dan memicu page splits yang mahal.
3. **Konsekuensi di MySQL** — Pada MySQL InnoDB, primary key adalah clustered index, sehingga random UUIDv4 akan memfragmentasi seluruh baris tabel di dalam disk.
4. **Solusi: UUIDv7** — UUIDv7 menempatkan timestamp 48-bit di awal identifier, membuat kunci baru tetap berurutan di dalam B-Tree layaknya sequential integer.
5. **Lonjakan Performa** — Penggunaan UUIDv7 memangkas ukuran index hampir separuhnya dan mengembalikan sequential write throughput tanpa kehilangan sifat unik global.
6. **Checklist Migrasi** — Pastikan tidak menyimpan UUID sebagai VARCHAR(36) atau TEXT, serta gunakan tipe data native UUID untuk efisiensi maksimal.
