**Angle:** Ide ini membahas pentingnya code review yang mendalam sebagai 'kontrak operasional', bukan sekadar formalitas, terutama dengan hadirnya AI coding. Ini memberikan tips praktis untuk developer dalam melakukan review yang berkualitas.

**Slide-by-slide:**
1. **Code Review: Bukan Sekadar Formalitas** — Sering kan nemu PR (Pull Request) ratusan baris, terus langsung kasih 'LGTM' doang? Hati-hati, lho! Code review itu bukan cuma formalitas, tapi 'kontrak operasional' yang menentukan kualitas dan keamanan kode kita.
2. **Dampak AI pada Code Review** — Dengan bantuan AI coding assistant, kode bisa dihasilkan lebih cepat dan terlihat bersih. Ini justru meningkatkan godaan untuk 'rubber-stamp' PR tanpa review mendalam. Padahal, AI juga bisa berhalusinasi atau menghasilkan kode yang kurang optimal.
3. **PR = Operational Contract** — Bayangkan PR sebagai kontrak operasional. Kode yang di-merge akan berjalan di produksi dan punya dampak nyata. Setiap baris kode yang masuk harus memenuhi standar, baik dari segi fungsionalitas, performa, maupun keamanan.

5. **Peran Aktif Reviewer** — Jangan pasif! Ajak diskusi, minta klarifikasi, atau sarankan alternatif yang lebih baik. Reviewer yang baik tidak hanya menunjukkan kesalahan, tapi juga menawarkan solusi dan pemahaman yang lebih dalam.
6. **Kesimpulan: Investasi Waktu yang Worth It** — Melakukan code review secara menyeluruh memang butuh waktu dan effort. Tapi, investasi ini akan sangat worth it untuk menghindari masalah di masa depan, menjaga kualitas kode, dan membangun tim yang lebih solid. Mari jadi reviewer yang lebih bertanggung jawab!

### 2. AWAS! Dependencies GitHub Actions Bisa 'Diracuni'?! Lindungi Workflow-mu! _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Konten ini membahas risiko keamanan dalam penggunaan GitHub Actions, khususnya potensi serangan melalui dependency yang 'diracuni'. Ini memberikan tips praktis untuk developer tentang cara melindungi workflow CI/CD mereka.

**Slide-by-slide:**
1. **Bahaya 'Poisoned' GitHub Actions** — Kamu pakai actions/checkout@v4 di workflow GitHub Actions? Tahukah kamu bahwa tag seperti v4 bisa diganti oleh maintainer yang dikompromikan? Ini berarti workflow-mu bisa saja menjalankan kode berbahaya tanpa disadari!
2. **Ancaman di Balik Kemudahan** — GitHub Actions sangat memudahkan, tapi juga jadi target menarik bagi penyerang. Jika tag versi pada action dipindahkan ke kode berbahaya, pipeline CI/CD-mu akan mengeksekusi kode tersebut dengan akses penuh ke repositori dan rahasia sensitif.
3. **Kenapa Tag Versi Rawan?** — Tag versi (seperti v4) sifatnya bisa bergerak (mutable). Maintainer bisa memindahkan tag ini ke commit lain. Jika akun maintainer diretas, penyerang bisa memindahkan tag ke versi yang mengandung malware atau backdoor.
4. **Solusi: Gunakan SHA Komit!** — Cara teraman adalah menggunakan SHA komit (commit SHA) spesifik dari action. Contohnya: actions/checkout@b0864380962315a6b7d5a083f2a1bb43b817c767. Ini memastikan workflow-mu selalu menggunakan versi kode yang sudah diverifikasi dan tidak berubah.
5. **Cara Menemukan SHA Komit** — Kamu bisa menemukan SHA komit terbaru dari sebuah action di halaman GitHub repository-nya. Cari commit terbaru dari tag yang kamu gunakan, lalu salin SHA-nya. Pastikan untuk selalu memverifikasi SHA yang kamu gunakan.
6. **Keamanan CI/CD, Tanggung Jawab Kita** — Mengamankan pipeline CI/CD adalah tanggung jawab bersama. Dengan menggunakan SHA komit, kita bisa mengurangi risiko serangan dan menjaga integritas proyek. Jangan biarkan kemudahan menjadi celah keamanan!

### 1. Stop Samakan Container Queries dengan Media Queries! Ini Bedanya & Kenapa Penting! _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Konten ini menjelaskan perbedaan fundamental antara CSS Container Queries dan Media Queries, serta kapan dan bagaimana menggunakan masing-masing untuk membangun komponen web yang responsif dan adaptif secara alami.

**Slide-by-slide:**
1. **Container Queries vs. Media Queries** — Sering keliru menyamakan CSS Container Queries dengan Media Queries? Meskipun keduanya untuk responsivitas, cara kerjanya sangat berbeda lho! Mari kita bedah perbedaannya.
2. **Media Queries: Responsifitas Global** — Media Queries bekerja berdasarkan ukuran viewport (layar) secara keseluruhan. Kamu mengatur styling untuk seluruh halaman ketika lebar browser mencapai titik tertentu. Cocok untuk tata letak halaman utama.
3. **Container Queries: Responsifitas Komponen** — Container Queries membuat komponen merespons ukuran container induknya, bukan viewport. Artinya, satu komponen bisa punya tampilan berbeda tergantung di mana ia diletakkan, tanpa peduli ukuran layar global. Ini revolusioner!
4. **Kapan Pakai yang Mana?** — Gunakan Media Queries untuk layout halaman secara makro (misalnya: sidebar muncul di desktop, hilang di mobile). Gunakan Container Queries untuk komponen mikro (misalnya: card produk yang menyesuaikan diri di sidebar atau main content).
5. **Manfaat Container Queries** — Dengan Container Queries, komponen jadi lebih mandiri (self-contained) dan reusable. Kamu tidak perlu lagi menulis ulang CSS untuk setiap konteks yang berbeda. Desain jadi lebih modular dan mudah dikelola.
6. **Mulai Beradaptasi!** — Meski sudah didukung di banyak browser, Container Queries masih banyak yang belum memaksimalkan. Yuk, mulai pelajari dan terapkan di proyekmu. Ini akan sangat membantu dalam membangun UI yang fleksibel dan powerful!

### 3. Punya Aplikasi di HP Lipat? JANGAN Cuma Di-Stretch Doang! _(Format: Story — konten cepat & spontan, cocok quick tips/teaser, otomatis hilang dalam 24 jam)_

**Angle:** Peringatan cepat tentang kesalahan umum dalam mendesain aplikasi untuk perangkat foldable/layar lipat. Fokus pada pentingnya adaptasi desain yang cerdas, bukan hanya meregangkan UI, untuk pengalaman pengguna yang optimal.

**Slide-by-slide:**
1. **HP Lipat = Layar Luas!** — Smartphone lipat kini makin populer! Layarnya yang bisa meluas menawarkan banyak potensi. Tapi, jangan sampai salah desain ya!
2. **Jangan Cuma Di-Stretch!** — Banyak yang cuma meregangkan (stretch) tampilan aplikasi lama ke layar lebih besar. Hasilnya? UI jadi aneh, elemen jauh, dan pengalaman user jadi buruk. Big NO!
3. **Pikirkan Aliran Konten** — Layar yang lebih besar berarti lebih banyak ruang untuk konten dan interaksi. Tata ulang elemen, manfaatkan ruang untuk multitasking, atau tampilkan detail lebih banyak. Ini kesempatan lho!
4. **Manfaatkan 'Fold' & 'Hinge'** — Beberapa perangkat lipat bisa ditekuk dan punya 'hinge' (engsel). Pikirkan bagaimana ini bisa jadi bagian dari UX yang inovatif, misal untuk split-screen view atau mode tenda.
5. **Desain Ulang, Bukan Cuma Resize** — Intinya, desainlah ulang aplikasi untuk foldable, bukan cuma resize. Pikirkan ulang bagaimana user berinteraksi dengan layar yang fleksibel ini. Pengalaman yang mulus, user makin happy!
