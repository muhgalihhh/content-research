**Angle:** Menjelaskan konsep database indexing dan B+ tree secara visual dan analogis agar developer paham kenapa index bisa memangkas latency hingga hitungan milidetik.

**Slide-by-slide:**
1. **Analoginya Seperti Buku Tebal** — Bayangkan kamu mau cari topik tertentu di buku setebal seribu halaman. Apakah kamu bakal baca halaman per halaman dari awal? Jelas makan waktu lama. Kamu pasti langsung buka Daftar Isi untuk langsung lompat ke bab yang tepat. Nah, database index bekerja dengan konsep persis seperti itu.
2. **Eksperimen Query di PostgreSQL** — Dalam pengujian pada jutaan data tabel penumpang, pencarian filter nama dan account_id tanpa index butuh waktu 5 detik di Mac M1. Kenapa lambat? Karena database melakukan Sequential Scan—memeriksa satu per satu baris yang ada di disk memory.
3. **Keajaiban Index: Dari 5 Detik Jadi 1 ms** — Begitu index komposit dibuat pada kolom tersebut, waktu eksekusi query langsung anjlok jadi 1 hingga 10 milidetik. Biaya komputasi query (cost) turun drastis dari 274.633 menjadi hanya 8,46—artinya beban kerja database berkurang lebih dari 32.000 kali lipat!
4. **Di Balik Layar: Struktur B+ Tree** — Index bukan sulap, melainkan struktur data B-Tree atau B+ Tree. Data dipecah menjadi node akar, internal, dan daun. Pada B+ tree, data pointer disimpan di daun, sementara node atas berfungsi sebagai rute navigasi cepat tanpa membaca seluruh baris data.
5. **Clustered vs Non-Clustered Index** — Clustered index mengatur ulang letak fisik penyimpanan data di disk (hanya ada 1 per tabel, sangat cepat untuk pencarian range dan sorting). Sementara non-clustered index membuat struktur data terpisah berisi nilai terindeks dan pointer ke data fisik aslinya.
6. **Mulai Cek Query Plan Kamu** — Sebelum buru-buru upgrade kapasitas database, coba jalankan EXPLAIN ANALYZE pada query kamu. Pasang index pada kolom yang sering masuk klausa WHERE atau JOIN, dan rasakan lonjakan performanya seketika!

**Slide-by-slide:**
1. **Timeout Bukan Berarti Gagal** — Status timeout artinya client tidak menerima respons sebelum batas waktu habis. Server mungkin sudah menerima dan memprosesnya, tapi respons terputus di jaringan. Timeout adalah kondisi 'unknown', bukan 'failed send'.
2. **Jebakan Retry Membabi Buta** — Langsung mengirim ulang request setiap kali timeout adalah biang keladi kenapa satu laporan transaksi bisa terkirim tiga kali ke customer. Retry hanya boleh dilakukan jika kamu punya mekanisme Idempotency Key!
3. **Pisahkan Bikin Lampiran dari Web Request** — Jangan render attachment PDF/Excel di dalam siklus HTTP request utama. Lempar prosesnya ke durable job worker. Request web cukup mengembalikan report_id agar user tidak tertahan latensi rendering dokumen besar.
4. **Kunci File dengan Hash** — Hitung digest hash byte lampiran sekali saja. Pastikan worker memakai file artefak yang sama untuk proses retry agar identitas pesan tidak berubah-ubah dan tidak memicu pengiriman ganda di sisi provider.
5. **Terapkan di Sistemmu** — Pisahkan timer DNS, koneksi, dan upload payload secara terukur. Sistem transaksional yang andal selalu siap menghadapi kegagalan jaringan tanpa merusak pengalaman customer!
