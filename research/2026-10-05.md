**Angle:** Memberikan panduan praktis dan cost-effective bagi developer untuk membuat HTTP tunnel pribadi yang aman, tanpa bergantung pada layanan pihak ketiga.

**Slide-by-slide:**
1. **Pengenalan HTTP Tunnel Sendiri** — Kenapa sih perlu HTTP tunnel? Ini buat ng expose layanan lokal ke internet dengan aman, cocok buat testing webhook atau aplikasi yang masih di dev. Solusi gratis dan powerful daripada layanan berbayar.
2. **Keuntungan Self-Hosted** — Dengan self-hosted, kamu punya kontrol penuh atas data, lebih aman, dan hemat biaya karena tidak perlu langganan. Plus, kamu bisa kustomisasi sesuka hati sesuai kebutuhan proyekmu.
3. **Persiapan: SSH & Nginx** — Pastikan kamu punya server dengan akses SSH dan Nginx terinstal. Nginx akan jadi reverse proxy-nya, dan SSH bakal jadi jalur aman buat tunneling. Ini fondasi setup kita.
4. **Langkah 1: Setup SSH Tunnel** — Buat SSH tunnel dari lokal ke server. Ini akan membuat port di server mem-forward trafik ke port di mesin lokalmu. Cukup satu perintah simpel di terminalmu!
5. **Langkah 2: Konfigurasi Nginx** — Di server, konfigurasi Nginx untuk menerima koneksi HTTP dan mem-proxy-kannya ke port lokal yang sudah ter-tunnel oleh SSH tadi. Jangan lupa setup SSL biar lebih aman dan profesional.
6. **Tes & Optimalisasi** — Coba akses domain yang sudah dikonfigurasi. Kalau berhasil, berarti tunnel-mu sudah berjalan dengan baik! Pertimbangkan juga security hardening tambahan untuk proteksi maksimal.
7. **Lebih Lanjut: Automasi & Monitoring** — Untuk penggunaan jangka panjang, pertimbangkan automasi start/stop tunnel menggunakan systemd atau script. Setup monitoring dasar juga penting agar tunnel selalu berjalan lancar tanpa gangguan.

### 2. Sering ketemu string Base64 di JavaScript dan bingung cara balikin ke data aslinya? Ini dia trik jitu yang wajib kamu tahu! _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Memberikan panduan singkat namun esensial tentang cara decoding Base64 di JavaScript, termasuk pitfalls umum dan solusi praktis untuk menangani karakter UTF-8.

**Slide-by-slide:**
1. **Apa itu Base64? Kenapa Perlu Decode?** — Base64 adalah metode encoding untuk mengubah data biner jadi teks ASCII, sering dipakai buat transfer data di URL, API, atau embed gambar. Kita perlu decode buat balikin ke format aslinya agar bisa digunakan.
2. **The Classic: `atob()` dan `btoa()`** — Browser punya fungsi bawaan JavaScript yang powerful: `atob()` untuk decode dan `btoa()` untuk encode. Sekilas memang simpel banget, tapi ada jebakan kecil yang sering bikin developer kebingungan atau error.
3. **Jebakan Karakter UTF-8** — Masalahnya, `atob()` dan `btoa()` itu didesain cuma untuk string Latin-1. Kalau ada karakter UTF-8 (misalnya emoji, aksara non-Inggris, atau karakter khusus), fungsi ini bakal error atau menghasilkan output yang rusak.
4. **Solusi Aman: `encodeURIComponent` & `decodeURIComponent`** — Triknya adalah dengan melakukan encoding terlebih dahulu string UTF-8 pakai `encodeURIComponent` sebelum di `btoa()`. Untuk decode, urutannya dibalik: `atob()` lalu `decodeURIComponent`. Ini memastikan semua karakter tertangani dengan baik.
5. **Contoh Penerapan di Real World** — Dari token JWT, data URL gambar, sampai parameter query, decoding Base64 adalah skill fundamental bagi setiap developer. Yuk, kita lihat beberapa contoh penggunaannya di skenario pengembangan aplikasi nyata!
6. **Tool Gratis untuk Decode Instan** — Kadang kita butuh cara cepat buat ngecek atau decode string Base64. Ada banyak tool online gratis yang bisa bantu proses ini dengan instan. Manfaatkan tool-tool tersebut untuk efisiensi kerjamu!

### 1. Kamu masih pakai Media Queries buat semua responsive design? Saatnya kenalan sama Container Queries, game-changer yang sering salah kaprah! _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Menjelaskan perbedaan fundamental antara Container Queries dan Media Queries, serta kapan dan bagaimana menggunakan Container Queries secara efektif untuk desain yang lebih adaptif dan reusable.

**Slide-by-slide:**
1. **Media Queries vs. Container Queries** — Media Queries responsif terhadap ukuran *viewport* browser secara keseluruhan. Sebaliknya, Container Queries responsif terhadap ukuran *container* induknya. Ini adalah perbedaan mendasar yang powerful!
2. **Masalah dengan Media Queries Tradisional** — Sulit membuat komponen UI yang benar-benar reusable dengan Media Queries. Setiap komponen seringkali perlu tahu ukuran kontainer tempat dia berada, bukan ukuran layar global, yang membuat CSS jadi kaku.
3. **Kekuatan Container Queries** — Bayangkan satu komponen kartu (card) yang bisa berubah layout-nya otomatis tergantung seberapa besar area tempat dia diletakkan, bukan ukuran browser! Itu adalah esensi dari Container Queries yang sangat fleksibel.
4. **Kapan Pakai Container Queries?** — Container Queries ideal untuk mendesain komponen mandiri seperti widget, card, atau module. Mereka bisa adaptif, baik saat diletakkan di sidebar kecil maupun di area konten utama yang lebar, tanpa perlu banyak penyesuaian.
5. **Cara Penerapan Praktis** — Cukup tambahkan properti `container-type` dan `container-name` ke elemen induk yang ingin responsif. Setelah itu, gunakan aturan `@container` di CSS untuk mendefinisikan styling responsifnya berdasarkan ukuran kontainer.
6. **Contoh Before-After (Konseptual)** — Lihat bagaimana satu komponen search bar bisa punya layout horizontal yang elegan di area lebar, dan secara otomatis berubah menjadi layout vertikal di area sempit. Semua ini terjadi otomatis, tanpa Media Query yang rumit.
7. **Tips UX/UI: Desain Komponen yang Fleksibel** — Dengan Container Queries, kita bisa fokus mendesain komponen yang 'cerdas' dan fleksibel. Ini adalah kunci untuk membangun sistem desain yang scalable, mudah di-maintain, dan adaptif di berbagai konteks.

**Slide-by-slide:**
1. **Dashboard yang Membosankan vs. Bermanfaat** — Banyak dashboard cuma jadi 'wall of data' yang bikin overwhelm dan sulit dipahami. Padahal, tujuan utama dashboard itu mendorong *insight* dan *action*, bukan cuma *information display*.
2. **Mulai dari Pertanyaan, Bukan Data** — Sebelum buka tool data visualization, tanya dulu: 'Keputusan apa yang ingin diambil pengguna?' atau 'Masalah apa yang ingin mereka selesaikan?' Ini adalah fondasi desain yang impactful.
