**Angle:** Menjelaskan cara mengamankan eksekusi agen AI Python dari ancaman overwrite berkas sensitif menggunakan pustaka standar tanpa dependensi pihak ketiga.

**Slide-by-slide:**
1. **Bahaya Akses File Agen AI** — Saat agen AI atau LLM membuat dan menulis berkas secara otomatis, risiko keamanan muncul jika model mengalami halusinasi atau prompt injection. Tanpa validasi ketat, agen bisa melakukan directory traversal atau menimpa berkas sensitif seperti .env dan .ssh/authorized_keys.
2. **Mengenal AgentWritePathResolver** — Untuk mencegah eksekusi path berbahaya, kita bisa memanfaatkan skrip AgentWritePathResolver. Skrip ini bertindak sebagai mesin kebijakan keamanan yang memeriksa dan memverifikasi path sebelum modifikasi disk diizinkan. Skrip ini murni dibuat dengan Python standard library minimal versi 3.8.
3. **11 Langkah Verifikasi Ketat** — Resolver ini menjalankan 11 tahapan validasi terhadap path yang diminta. Pemeriksaan dimulai dari penyaringan karakter kontrol dan null byte injection sebelum path diproses lebih jauh di sistem file. Jika direktori kerja tidak ditemukan, sistem langsung membatalkan eksekusi.
4. **Proteksi Symlink Escape** — Memanggil fungsi resolve bawaan pada path yang belum ada bisa gagal mendeteksi symlink luar. Skrip ini menggunakan metode _safe_canonicalize untuk menelusuri direktori induk selangkah demi selangkah. Jika konfigurasi disallow_symlinks diaktifkan, traversal symlink ke luar direktori kerja akan ditolak.
5. **Aturan Denylist dan File Tersembunyi** — Setelah dipastikan berada di dalam workspace_root, path relatif diperiksa terhadap DEFAULT_DENY_PATTERNS. Opsi deny_hidden=True juga akan menolak path tersembunyi seperti .config/test.json. Selain itu, file yang ada tapi bersifat read-only akan ditolak dengan alasan EXISTING_FILE_READONLY.
6. **Kesimpulan Keamanan Agen AI** — Mengizinkan agen membuat file tanpa pembatas adalah celah fatal dalam pengembangan software berbasis AI. Dengan menerapkan AgentWritePathResolver pada loop eksekusi alat kamu, seluruh jalur penulisan file terpantau aman dan terisolasi sempurna di direktori proyek.

**Slide-by-slide:**

Akibatnya saat disalin ke repositori kosong, pipeline tersebut gagal berjalan. Kita membutuhkan contoh alur kerja lengkap di file .github/workflows/ci-cd.yml yang siap eksekusi.
2. **4 Tahap Berurutan dan deploy.sh** — Pipeline ini membagi alur menjadi empat tahap yaitu linting, testing, pembuatan Docker image, dan penyebaran aplikasi. Karena tidak ada skrip deployment generik yang berlaku universal, kamu tinggal menyediakan file deploy.sh yang sesuai dengan infrastruktur server tujuan kamu.
3. **Urutan Pekerjaan Berdasarkan Biaya** — Pengujian dijalankan pada setiap Pull Request karena biaya komputasinya paling murah. Pembuatan container image hanya dipicu jika pengujian sukses di branch main. Sedangkan deployment memiliki biaya paling tinggi karena berdampak langsung ke pengguna, sehingga ditaruh di tahap paling akhir.
4. **Pentingnya SHA Tag dan Concurrency** — Image Docker disarankan menggunakan tag github.sha alih-alih tag latest agar setiap rilis mengarah tepat ke satu commit spesifik. 5. **Optimasi Caching npm dan Docker** — File alur ini mengaktifkan dua jenis cache sekaligus. Opsi cache: npm pada setup-node menyimpan unduhan tarball berdasarkan hash lockfile, sementara cache-from dan cache-to dengan mode=max menyimpan layer intermediate Docker BuildKit agar build berikutnya berjalan jauh lebih cepat.
6. **Gerbang Persetujuan Manual Produksi** — Menambahkan baris environment: production mengunci tahap deployment di balik persetujuan manusia pada menu Settings GitHub. Pengaturan ini mendukung hingga enam peninjau, dan kamu bisa mengaktifkan opsi pencegahan self-approval agar pembuat PR tidak bisa menyetujui rilisnya sendiri.
