### 1. Masih sering bingung bedain kapan harus pakai Hash, List, atau Set di Redis? _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Banyak developer hafal perintah dasar Redis, tapi mendadak bingung saat menentukan struktur data yang pas untuk use-case nyata seperti cart belanja atau leaderboard.

**Slide-by-slide:**
1. **Masalah Klasik: Hafal Sintaks, Lupa Desain** — Nonton video tutorial Redis berkali-kali gampang bikin kita paham perintah SET dan GET. Tapi begitu diminta mendesain key untuk keranjang belanja atau activity feed, kita sering buka dokumentasi dari nol lagi.
2. **Strings & Hashes: Kapan Pilih Mana?** — Strings adalah default untuk single blob atau counter (seperti INCR page views) dan JSON yang tidak pernah diupdate parsial. Begitu kamu butuh update per field tanpa menimpa seluruh objek, beralihlah ke Hashes.
3. **Lists vs Sets: Soal Urutan dan Duplikasi** — Lists cocok untuk antrean tugas (LPUSH/BRPOP) atau timeline aktivitas terakhir karena mempertahankan urutan dan membolehkan duplikasi. Kalau kamu butuh anggota unik tanpa peduli urutan—misalnya daftar ID user online—gunakan Sets.
4. **Sorted Sets: Solusi yang Sering Terlewat** — Jangan paksakan menyimpan ranking skor ke dalam indeks List. Sorted Sets memberikan skor pada setiap entitas unik, menjadikannya pilihan sempurna untuk leaderboard, delayed jobs, hingga rate limiter berbasis timestamp.
5. **Cheat Sheet Sederhana Buat Sticky Note** — Ingat rumus praktis ini: Satu nilai tunggal pakai String. Kolom bernama dalam satu entitas pakai Hash. Berurutan dan boleh duplikat pakai List. Unik tanpa urutan pakai Set. Unik berurutan pakai Sorted Set.
6. **Latih Retrival, Jangan Cuma Nonton** — Tutup browsermu dan coba jawab skenario nyata secara mandiri seminggu sekali. Gesekan saat berpikir tanpa melihat dokumentasi itulah yang bikin insting arsitektur datamu benar-benar melekat di produksi.

### 2. Filter data di frontend itu ilusi keamanan: database kamu tetap bisa dibobol lewat console browser! _(Format: Feed — carousel evergreen, tersimpan di grid & gampang ditemukan lewat search/profil)_

**Angle:** Mengedukasi developer tentang pentingnya Row Level Security (RLS) di database PostgreSQL/Supabase dan jebakan infinite recursion yang sering bikin pusing.

**Slide-by-slide:**
1. **Filter Aplikasi Bukanlah Benteng** — Menulis filter seperti `.eq('buyer_id', user.id)` di aplikasi cuma memfilter tampilan. Pengguna mana pun bisa membuka console browser lalu menjalankan query tanpa filter untuk melihat seluruh transaksi pengguna lain.
2. **Row Level Security (RLS) Sebagai Solusi** — Dengan RLS, database sendiri yang menolak mengembalikan baris yang tidak boleh dilihat oleh pemanggil query. Kunci anon publik Supabase di browser tetap aman karena semua kontrol akses dijaga ketat di level tabel database.
3. **Jangan Cuma Bikin Policy SELECT** — Kesalahan umum pemula adalah hanya melindungi hak baca. Ingat bahwa setiap operasi INSERT, UPDATE, dan DELETE membutuhkan policy terpisah agar user tidak bisa mengubah data atau menaikkan hak akses milik mereka sendiri.
4. **Waspada Jebakan Infinite Recursion** — Jika Policy di Tabel A memeriksa Tabel B, sementara Tabel B juga memeriksa Tabel A, Postgres akan mengalami loop tak berujung. Solusinya, pindahkan lookup cross-table ke dalam helper function dengan atribut SECURITY DEFINER.
5. **Karakter Silent Fail pada RLS** — RLS biasanya tidak melempar error saat user mencoba membaca data terlarang, melainkan mengembalikan nol baris secara diam-diam. Saat menulis automated test, pastikan kamu menguji jumlah baris yang kembali, bukan sekadar ketiadaan error.
6. **Aturan Emas Membangun Fitur Baru** — Terapkan alur kerja terbalik yang aman: aktifkan RLS terlebih dahulu, tulis policy aksesnya, baru rancang UI aplikasi. Jangan pernah merilis tabel produksi tanpa policy akses yang telah diuji sebagai user asing!

**Angle:** Solusi cepat dan praktis untuk developer Python yang memakai package manager modern uv ketika menghadapi konflik wheel versi baru.

**Slide-by-slide:**
1. **Misteri Error Pasca Upgrade Python** — Baru upgrade runtime Python (misalnya ke versi 3.15) tapi saat jalankan `uv run pytest` malah muncul pesan error dependency yang membingungkan? Kamu tidak sendirian menghadapi isu ini.
2. **Tersangka Utama: uv.lock** — Perintah uv sering meninggalkan file `uv.lock` otomatis di lokal. File ini mengunci versi dependensi lama yang barangkali belum merilis pre-built wheel untuk versi Python terbaru yang kamu gunakan.
3. **Solusi Cepat 5 Detik** — Aturan praktisnya sangat sederhana: Jika ragu, langsung hapus file `uv.lock` di folder proyekmu! Setelah dihapus, jalankan kembali command test atau run kamu dari terminal.
4. **Resolusi Ulang Bersih** — Dengan menghapus file lock tersebut, uv akan melakukan re-resolve dependensi secara bersih dan mencari versi paket yang kompatibel dengan versi Python yang sedang aktif.
5. **Tips Khusus Pengembang Library** — Untuk proyek open-source library, pastikan `uv.lock` masuk ke `.gitignore` agar tidak membatasi fleksibilitas environment pengguna atau library lain yang mengonsumsinya.
